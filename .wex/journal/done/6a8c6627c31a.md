# Inventaire rafraîchi tout seul en debug

Question de départ : « comment un nouvel élément remonte-t-il dans l'inventaire
sans relancer une commande ? »

## Fait, testé en vrai

`InventoryExtension` a deux réponses à la même question, et c'est le kernel qui
choisit :

- **production** : lit les `elements.json` écrits, comme avant ;
- **debug** : appelle `ElementRegistryService::compileAll()`, qui marche les
  assets. Le scan existait déjà et rend l'inventaire *et* les contradictions.

`ds_element_registry_problems()` expose les contradictions, que
`inventory.html.twig` affiche en `message_warning` suivi de la liste — la page
est dessinée quand même.

La compilation est mémoïsée : une marche par requête, pas une par fonction.

Câblage : `services.yaml` passe `$debug: '%kernel.debug%'`.

**Test réel** : composant créé à la main → apparu au rechargement sans aucune
commande, avec « found on disk but not declared » nommé en haut de page →
`seed-elements` → page propre → composant supprimé → disparu.

## Aussi fait

`PageService.php` : le bloc du trait fantôme est retiré. Prouvé mort —
`trait_exists('Wexample\SymfonyLoader\Service\SymfonyDesignSystemBundleClassTrait')`
rend `false`, le nom résolvait dans le mauvais namespace et la branche n'a jamais
tourné. `getTemplateLocationPrefix()` retombe sur `getControllerBundle()`, qui
fait la même chose génériquement. Libellés de menu vérifiés intacts.

## Abandonné, et pourquoi

Le découpage loader → DS (déplacer `ConfirmService`, sortir les chemins de
composant de `BannerService`/`OverlayService`, règle de remplacement dans
`App.loadServices`) : **entièrement annulé**.

Cause : dans cette app le même paquet a deux adresses. webpack résout
`@wexample/*` par `node_modules` (une copie, `file:` copie au lieu de lier),
ts-loader type-checke par `vendor` via les `paths` du tsconfig (le vivant).
Tant que copie et source disent la même chose, rien ne se voit — d'où des mois
de builds tranquilles. Déplacer un fichier les fait diverger et le watcher casse
sur des lignes que personne n'a éditées.

Une tentative d'alias webpack lisant les `paths` du tsconfig n'a pas suffi ;
annulée aussi. Le sujet est réel mais c'est un chantier d'outillage à lui seul,
pas un à-côté du registre.

Note : l'erreur `LiveUpdatesService` du watcher préexiste — fichier jamais
touché, confirmé par `git status`.
