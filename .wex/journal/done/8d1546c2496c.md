# `link:` pour les assets npm des paquets PHP

## Le mécanisme

Un paquet PHP qui livre des assets a deux faces : `vendor/wexample/<pkg>` (lié
par le hook composer) et `@wexample/<pkg>` côté npm, dont la source est
`vendor/…/assets`. Yarn 1 **copie** un `file:` et **lie** un `link:`.

Webpack et TypeScript lisent tous deux `vendor/` (alias et `paths` générés
depuis une seule liste par le loader). La copie n'est lue que dans un cas :
un fichier mappé par `paths` qui n'existe plus → TS retombe sur la résolution
node, entre dans la copie figée, et remonte des erreurs sur des fichiers que
personne n'a touchés.

## Fait

- `file:` → `link:` dans 5 apps : TRADING/manager, SYRTIS/manager, SYRTIS/api,
  app-board, MOJOE/design-system.
- `yarn install` dans les 3 conteneurs node qui tournaient (design_system,
  app_board, trader_manager) : lock réécrit, les 4 `@wexample/symfony-*` sont
  des liens. SYRTIS (conteneurs arrêtés) : le lock se réécrira au prochain
  setup, rien à faire.
- Knowledge DS : `contributing/assets-as-npm-package` (page dédiée) ; renvoi
  depuis `contributing/architecture`.
- Knowledge loader : section « Assets shipped by a PHP package » dans
  `readme/installation`.
- Commentaires : `encore.manifest.js` (bloc resolve), `TsconfigPathsSynchronizer`,
  hook `node::install_local` (pourquoi il ne lie pas les symfony-*).

## Reste

- Le watcher DS doit être relancé pour que le résolveur webpack oublie les
  anciens dossiers.
- Le knowledge se rend au build (`built/en/`), pas lancé ici.
