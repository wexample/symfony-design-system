# Découpler loader → design system (JS)

`grep DesignSystem symfony-loader/` ne rend plus que deux noms de classes du
loader lui-même (`AbstractDesignSystemController`, le namespace
`Controller\Pages\DesignSystem`). Côté PHP c'était déjà le cas.

## Fait

- `ConfirmService` → `symfony-design-system/assets/js/Services/`. Le loader ne
  s'en servait pas.
- `BannerService`, `OverlayService` (loader) : `static componentPath: string|null`
  + `InvariantViolationError` (`ERR_BANNER_COMPONENT_UNSET`,
  `ERR_OVERLAY_COMPONENT_UNSET`) si un appel en a besoin sans qu'il soit fixé.
- Le DS livre `js/Services/BannerService.ts` et `OverlayService.ts` : deux
  sous-classes qui fixent le chemin.
- `App.loadServices()` : une sous-classe du service déjà enregistré sous le même
  nom le remplace. Nécessaire parce que `super.getServices()` enregistre le base
  en premier, et parce que `ConnectionStatusNoticeService` tire le base en
  dépendance. Les deux ordres sont couverts.
- Imports repointés (14 fichiers : DS, démo, SYRTIS manager, app-board, MOJOE,
  TRADING). L'`OverlayService` DS est enregistré dans les 4 App qui en ont
  l'usage — TRADING inclus, il appelle `showStandalone()` dans
  `pages/currencies/{show,index}.ts`.
- Audit : chaque appelant de `showStandalone()` et chaque utilisateur de
  `BannerService` est dans une app qui enregistre la sous-classe DS. WEEGER et
  SYRTIS/api : aucun usage.
- Knowledge DS `contributing/architecture` : paragraphe sur les trois services.
- `tsc --noEmit` : aucune erreur dans un fichier touché (le reste est le bruit
  préexistant de résolution `@wexample/js-*` hors webpack).
