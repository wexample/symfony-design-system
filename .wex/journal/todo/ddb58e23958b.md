# Champ tags iso (twig / Vue / dynamic-form), modèle des champs standardisés

Opened: 2026-11-05
Updated: 2026-11-05
Author: agent:main (Syrtis)

## Besoin

Syrtis a un champ « stamps » (des étiquettes posées sur les messages) à trois endroits, qui ne se ressemblent pas. Il veut **un tronc commun** : un champ générique du DS, identique en twig et en Vue, que Syrtis spécialise par simple préréglage. Ce champ sert de **modèle** aux autres champs standardisés (Syrtis ou non) : un champ métier = un champ générique du DS + des options préréglées.

## Constat

- `assets/components/form/tags-input` :
  - **Vue** (`tags-input.vue`) : `modelValue`, `placeholder`, `separator`, `suggestions` (liste proposée) ;
  - **twig** (`tags-input.html.twig` + `tags-input.ts`) : pas de suggestions → les deux rendus ne sont pas iso.
  - Les tags sont des `.tags-input--tag` simples ; ailleurs le DS dit une étiquette par `marker` (ton, glyphe) — Syrtis affiche ses stamps en `marker` ton `cat-straw`, glyphe `ph:bold/tag`.
- symfony-forms `TagsInputType` (`separator` seul) → `form_theme.html.twig` bloc `tags_input_widget` → twig du DS. Aucune option de suggestions ni d'apparence.
- `FormDefinitionBuilder` : pas de type `tags` dans la norme → le champ part en `type: text`, valeur « a, b » ; `dynamic-form` le dessine en simple texte.

## À faire

- [x] `tags-input` **iso** twig / Vue : mêmes options, même markup (marker + ×, entrée, liste proposée), même comportement — la logique est écrite une fois, `js/Helper/TagsHelper.ts`, appelée par la vue et par le script twig.
- [x] **Suggestions** : liste fixe (`suggestions`, mots, `value => label` ou `{ value, label }`) et source distante (`suggestions_url`, `?q=` après une pause de frappe, réponse mots ou `{ value, label }`, nue ou sous `data` / `items`). Liste déroulante filtrée par la frappe, flèches + Entrée, Échap, les tags pris exclus.
- [x] **Apparence** par `marker` : `tone` (état ou catégorie, `cat-straw`) et `glyph`, un pour tout le champ.
- [x] `TagsInputType` : options `suggestions`, `suggestions_url`, `tone`, `glyph`, passées au thème et à `form_definition()`.
- [x] Norme : `web/tags_input.json` (json-schema 1.3.0). **Écart** : les mots sont dans `tags`, pas dans `value` (même raison que `key_value`). Le champ reste **posté en un texte joint** par le séparateur, des deux côtés — ce que `TagsInputType` lit déjà, et ce qui garde le champ utilisable sans script. `dynamic-form` le dessine par `tags-input`.
- [x] Patron **« champ standardisé »** documenté (symfony-forms `usage/overview`, DS `usage/form-fields`) et montré dans la démo : `DemoStampsInputType` (`getParent()` = `TagsInputType`, défauts seuls) et `demo-stamps-input` (`extends: TagsInput`, défauts des props, son id de template sur le markup générique, `getSuggestionsUrl()` comme point d'extension pour une route). Démo : portfolio `form/from-server`, `form/rendered`, `form/vue`.
