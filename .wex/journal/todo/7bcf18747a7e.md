# Agent dans les écrans Syrtis : workspace, éditeur de job, slots

Fil de conception ouvert le 2026-11-27 avec l'utilisateur. Objectif : que l'agent intégré sache agir dans les écrans propres à Syrtis (éditeur de scénario, pipelines), en commençant par un cas simple : **sélectionner un slot dans l'éditeur de job pour qu'il s'affiche dans l'éditeur de slot** (ou dans un panel s'il n'y a pas de widget — convention du workspace).

## Répartition de l'information (décidée)
1. **Contrat `.ai.yml`** du composant / de la vue — le *mode d'emploi*, statique, en anglais : ce qu'est la pièce, ses actions et leurs arguments. Existe déjà, marche pour une vue d'app comme pour un composant DS.
2. **État de l'instance** (`getAgentState`, `getAgentLabel`) — ce qui est vrai maintenant : widgets ouverts du workspace, slots de l'éditeur de job, slot sélectionné.
3. **Knowledge** — le *sens* : ce qu'est un slot (un nœud + son emplacement + sa config), un job, une request, comment les widgets se répondent. Onglet knowledge du dock ; plus tard un outil serveur `read_knowledge`. Le contrat y **renvoie par une clé**, il ne recopie pas.
4. Boutons de toolbar : déjà des nœuds DS (libellé) ; `agent_description` seulement si le libellé ne suffit pas.

## Principes
- **Exploration itérative** plutôt qu'agrégat de descriptions : ajouter `inspect_page({ node, depth })` pour descendre dans une pièce.
- **Une action rend ce qu'elle a provoqué** : `select_slot({ slot })` fait le geste de l'utilisateur (souris, clic, événement du workspace), **attend l'accusé de réception** de ce qui a pris la sélection (widget éditeur de slot, ou panel ouvert), puis rend `{ slot, shown_in: { widget, node } | 'panel' }`. L'agent ne connaît jamais le bus d'événements.
- Utilitaire générique à écrire : émettre, puis attendre l'accusé, avec un délai maximum.
