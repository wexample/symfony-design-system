# Skin axis — 4th theming dimension

## State

The axis exists. `skin` is a loader usage like `color_scheme`, declared after
it in the loading order, with one value so far: `default`. `margins` was
renamed `density` at the same time, so the model reads: `color_scheme` (the
light), `density` (how much per screen), `skin` (how things are drawn),
`animations` (motion — still without any file).

What moved, pixel-identical (the 80 token declarations of the dashboard layout
compile byte-for-byte the same, only the selector changed):

- `layouts/default/_layout.density.default.scss` — `--space-*`, `--size-*`,
  `--font-size-*` on `.usage-density-default`.
- `layouts/default/_layout.skin.default.scss` — `--radius-*`, `--shadow-*`,
  `--border-*` (the line, never its colour) on `.usage-skin-default`.
- `layouts/dashboard/` has both, delegating to default.
- Every app layout on a DS layout carries the two entry files (`layout.density.default.scss`,
  `layout.skin.default.scss`), as it does for the colour scheme.
- Demo: *Foundations › Skin* (radii, shadows, borders, separators); the radii
  left the spacing page.

## Where the cut is

- Colour → `color_scheme`, always. A skin says which *role* a component takes
  (`--tabs-surface: var(--color-info-8)`), the scheme says what that role is.
- Spacing, sizes, type *size* → `density`. Font *family* and weight → `skin`.
- Radii, shadow geometry, border width and style, separators, focus ring width
  → `skin`. Intrinsic shapes (a round avatar, a pill switch) are not skin
  decisions and stay written in the shape.
- Tokens first; a per-component file (`tabs.skin.<value>.scss`, which the
  loader already supports for any render node) only when tokens cannot say it.

## What remains

1. **Role tokens before a second skin.** Shapes read `--radius-1` directly (22
   times) and `tab` hard-codes `border-radius: 0`: a skin cannot round a tab
   that says 0. Introduce `--radius-control` / `--radius-surface` /
   `--radius-pill` (and the same for borders), have each shape read its role,
   and let each skin distribute. Not needed for `default`, needed before any
   other skin is expressive.
2. **Shadow colour is a leak.** `--shadow-N` carry a fixed `rgba(0,0,0,…)`,
   identical in dark and light. The skin should own the geometry and take the
   colour from a `--shadow-color` of the scheme.
3. **The second skin.** `default` mixes two sensibilities — square and
   functional with wide margins (menu, table), rounded tailwind-ish (buttons,
   blocks). Separating them is the first real pair: `square` and `fluid`
   (working names). Each is one token file per layout, plus the odd
   per-component file where structure changes.
4. `animations` is still a configured axis with no file: making it real means
   motion tokens and rewriting the hard-coded `transition` durations across
   shapes. A separate job.
5. Small: `chat` writes `border-radius: var(--space-2)`, `status` writes
   `100px` where `--radius-pill` exists.
