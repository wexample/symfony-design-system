# Skin axis — 4th theming dimension

## State

The axis exists. `skin` is a loader usage like `color_scheme`, declared after
it in the loading order, with one value so far: `default`. `margins` was
renamed `density` at the same time, so the model reads: `color_scheme` (the
light), `density` (how much per screen), `skin` (how things are drawn),
`animations` (motion — still without any file).

What moved, pixel-identical (the 80 token declarations of the dashboard layout
compile byte-for-byte the same, only the selector changed):

- `layouts/default/_layout.density.default.scss` — `--space-*`, `--size-*`,
  `--font-size-*` on `.usage-density-default`.
- `layouts/default/_layout.skin.default.scss` — `--radius-*`, `--shadow-*`,
  `--border-*` (the line, never its colour) on `.usage-skin-default`.
- `layouts/dashboard/` has both, delegating to default.
- Every app layout on a DS layout carries the two entry files (`layout.density.default.scss`,
  `layout.skin.default.scss`), as it does for the colour scheme.
- Demo: *Foundations › Skin* (radii, shadows, borders, separators); the radii
  left the spacing page.

## Where the cut is

- Colour → `color_scheme`, always. A skin says which *role* a component takes
  (`--tabs-surface: var(--color-info-8)`), the scheme says what that role is.
- Spacing, sizes, type *size* → `density`. Font *family* and weight → `skin`.
- Radii, shadow geometry, border width and style, separators, focus ring width
  → `skin`. Intrinsic shapes (a round avatar, a pill switch) are not skin
  decisions and stay written in the shape.
- Tokens first; a per-component file (`tabs.skin.<value>.scss`, which the
  loader already supports for any render node) only when tokens cannot say it.

## What remains

Done since: the **role tokens**. `_layout.skin.default.scss` declares
`--radius-control`, `--radius-surface`, `--radius-media` (plus the existing
`--radius-pill`), and no shape reads `--radius-1`/`--radius-2` any more — each
reads its role. The `border-radius: 0` resets (tab, colour-scheme switch)
are gone, the hand-written pills (`999px`, `100px`) read `--radius-pill`.
Verified by compiling every touched shape before and after: every residual
difference is value-identical. The rules are written up in
`.wex/knowledge/contributing/theme-axes.md.j2`.

1. **Shadow colour is a leak.** `--shadow-N` carry a fixed `rgba(0,0,0,…)`,
   identical in dark and light. The skin should own the geometry and take the
   colour from a `--shadow-color` of the scheme.
2. **The second skin is there, and is a draft.** `fluid` (pill controls, no
   separators, deeper shadows) exists to make the axis switchable and to prove
   the roles carry. It has not been looked at page by page.

3. **The rest of the second skin.** `default` stays the fallback and is named by intent,
   not by form (`basic` would do as well). The current look mixes two
   sensibilities — square and functional with wide margins (menu, table),
   rounded tailwind-ish (buttons, blocks); `fluid` is the rounded one. A skin
   is one token file per layout, plus the odd per-component file
   (`tabs.skin.<value>.scss`, already resolved by the loader) where structure
   changes. `windows95` is planned once the rest is settled: bevels, no
   radius, system font — its colours come through roles mapped onto the
   scheme, never as hex.
4. **Switching.** No header switch: the debug panel's *Usages* tab already
   lists every skin the config declares. A `select` may come later.
5. **Border roles**, if a skin ever needs a control border unlike a surface
   border — today `--border-default` serves both and nothing diverges.
6. `animations` is a configured axis with no file, and its list is down to
   `none` — a value that loads nothing is a switch that does nothing. Making it
   real means motion tokens and rewriting the hard-coded `transition` durations
   across shapes. Note it is *not* what animates a usage swap: that is
   `is-switching-usage`, posted by the loader and dressed by the theme.
