# Paquets git : php-git, symfony-git, symfony-git-ds (historique paginé par l'API)

Opened: 2026-10-16
Updated: 2026-10-16
Author: agent:addon:ai/editor (app-board)

## Contexte
Le board (app-board) a un outil « Git » dans le dock de chaque app : une toolbar avec l'interrupteur auto-commit à droite, et en dessous l'historique git de l'app. Pour l'instant, l'historique est rendu côté serveur : les 100 derniers commits, avec `graph_log` du DS. Certains projets ont des années d'historique, donc à terme il faut un historique **paginé et rechargeable**, ce qui veut dire passer par l'API et le modèle d'entité de la suite (DTO, schéma exporté, entité TypeScript, repository js-api).

## Où est le code git aujourd'hui (éparpillé)
- `symfony-helpers` / `Service/GitRepositoryReader.php` : `status`, `commit`, `log($repository, $limit, ?$path)`, `isBusy`.
- `symfony-wex` / `Service/WorkdirCommitter.php` : commite des chemins donnés, en tant que propriétaire du repo (`setpriv`).
- `symfony-design-system` / `Twig/GraphLogExtension.php` : `graph_log(commits)`, le dessin du graphe.
- `symfony-coding` / `Twig/GitGraphExtension.php` : pas un second graphe, mais l'adaptateur commits → items de `graph_log` (couleurs des refs, hash court, auteur). C'est le cœur de symfony-git-ds, à y déplacer.
- app-board : `AppCloner` (`git clone`), `AppWorkdirLinker`, `AppFileHistory`, `AppRepositoryState`.

## Proposition (validée par l'opérateur)
- **php-git** : la lecture (`log` paginé, `status`, `show`) et l'écriture (commit de chemins donnés). PHP pur sur `symfony/process`. Y déplacer `GitRepositoryReader` et le cœur de `WorkdirCommitter`. **Sans `setpriv`** : commiter en tant que propriétaire du `.git` quand on tourne en root est une contrainte des conteneurs wex, pas de git. php-git exécute git ; sous quelle identité il le lance reste à symfony-wex.
- **symfony-git** : le bundle. L'entité `Commit`, le `CommitRepository`, l'endpoint d'API paginé « commits d'un repository » (optionnellement filtré par chemin), son DTO.
- **symfony-git-ds** : le graphe git paginé, un entity collection manipulator (`AbstractEntityCollectionVueMixin`) branché sur le repository js-api généré, qui dessine avec le `graph-log` du DS. Il remplace `GitGraphExtension` (symfony-coding), **pas** `graph_log`.
- **DS** : `graph-log` reste dans le DS, générique (`{ id, parents, title, href, refs, code, meta, date }`, rien de git). À y faire : `GraphLogHelper` calcule les couloirs sur la liste entière ; il doit accepter des items ajoutés à la suite (page suivante) sans tout recalculer.

## Point tranché : un commit est une entité de la suite, non persistée
Norme symfony-api respectée de bout en bout : entité, DTO, pseudocode YAML, `api:export:entities`, entité et repository TypeScript générés. Rien n'y dépend de Doctrine :
- `api:export:entities` part du YAML pseudocode, pas des métadonnées Doctrine ;
- `AbstractApiController::apiResponsePaginated()` prend un tableau d'items et un total facultatif (sans total, le pager se dégrade en précédent/suivant).

Ce qui en découle :
- **Pas de `#[ORM\Entity]`, pas de table.** Le repository garde son rôle et ses noms de méthodes (`findPage(repository, page, length, ?path)`, `find(hash)`), mais lit `.git` via php-git au lieu d'étendre `ServiceEntityRepository`. `apiResponseQueryPage()`, qui prend un `QueryBuilder`, ne sert pas ici.
- **Identité stable.** `AbstractEntity` crée un `Uuid::v7()` aléatoire : un commit relu aurait un autre id, ce qui casse la pagination et le rechargement côté manipulator. Prendre un `Uuid::v5()` dérivé du dépôt et du hash (comme les ids d'apps du board), le hash restant un champ.
- **Pas de `createNew{Entity}()` / `saveNew`** : un commit se crée par git, pas par `persist`.
- **Pas de live updates** (ils reposent sur les events Doctrine) : l'historique se rafraîchit à la demande.

## Consommateurs à migrer ensuite
- app-board : l'outil Git (historique de l'app) et l'historique d'un fichier (`file_history`, `AppFileHistory`).
- Tout ce qui utilise `graph_log` ou le graphe de symfony-coding.
